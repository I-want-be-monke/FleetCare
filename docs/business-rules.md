# FleetCare — Business Rules

## 1. Автомобили

Каждый автомобиль имеет:

- Уникальный идентификатор.
- Название.
- Текущий пробег.
- Пробег последнего технического обслуживания.
- Интервал технического обслуживания.

Пробег не может быть отрицательным или уменьшаться.

Интервал технического обслуживания должен быть положительным числом.

## 2. Плановое техническое обслуживание

Если:

`CurrentOdometerKm - LastServiceOdometerKm >= ServiceIntervalKm`

то автомобиль требует планового технического обслуживания.

Если открытой заявки на плановое ТО нет, система создаёт новую заявку со статусом `New`.

## 3. Коды неисправностей

Если показание телеметрии содержит код неисправности (`FaultCode`), система создаёт заявку с указанием этого кода.

Разные коды неисправностей считаются разными причинами.

## 4. Предотвращение дублирования

У одного автомобиля может быть не более одной открытой заявки по одной причине.

Повторная проверка того же события не должна создавать дублирующую заявку, даже если исходная заявка уже закрыта.

## 5. Статусы заявок

Заявки могут находиться в одном из состояний:

- `New` — новая заявка.
- `InProgress` — заявка в работе.
- `Completed` — заявка завершена.

Заявка считается открытой, пока её статус не равен `Completed`.

## 6. Завершение технического обслуживания

При завершении заявки на плановое ТО пробег последнего обслуживания автомобиля обновляется до текущего пробега.

Завершение заявки по коду неисправности не изменяет пробег последнего ТО.

## 7. Обработка сообщений

Для последующей интеграции с Kafka предусмотрены сущности:

- `OutboxMessage` — событие, подготовленное к публикации.
- `ProcessedMessage` — идентификатор сообщения, уже обработанного конкретным обработчиком.

Хранение сообщений, транзакции и ограничения уникальности будут реализованы на уровне PostgreSQL и фоновых обработчиков.

## 8. Проверки

Бизнес-правила должны проверяться модульными тестами без HTTP API, PostgreSQL, Kafka и Python.
