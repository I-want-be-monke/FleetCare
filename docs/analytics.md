# FleetCare Python Analytics

## Назначение

Обработчик читает `telemetry.recorded.v1`, сверяет сообщение с сохранённым
показанием PostgreSQL, анализирует температуру и при обнаружении устойчивого
отклонения публикует `risk.detected.v1`. .NET Worker сохраняет предупреждение,
которое диспетчер видит на `/dashboard/risks`.

Это учебная аналитика на сгенерированной телеметрии. Оценка `score` показывает
силу отклонения, а не вероятность поломки.

## Алгоритм

Для очередного события выбираются последние девять показаний автомобиля не
позднее времени этого события. Анализируются последние восемь: медиана первых
пяти служит базой, следующие три должны не снижаться и каждое должно быть
минимум на 8 °C выше базы. При меньшем числе показаний результат `insufficient`.
Если предыдущее окно уже выявляло тот же рост, новое предупреждение не создаётся.

`score = min(1, минимальное_отклонение / 20)`.

Пример: `80, 81, 80, 79, 80, 90, 92, 94, 96`. На восьмом показании медиана
равна 80 °C, минимальное отклонение равно 10 °C, `score = 0.5`. Девятое
показание не создаёт повтор. Простое правило «температура > 100 °C» на этих
данных не сработало бы. Настройки алгоритма подобраны для демонстрации;
нагрузка двигателя и погода пока не учитываются.

## Локальный запуск

Из корня репозитория:

```powershell
docker start fleetcare-pg-step3 fleetcare-kafka-step5
py -m venv .venv                       # только при первом запуске
.\.venv\Scripts\python.exe -m pip install -r analytics\requirements.txt
.\.venv\Scripts\python.exe -m pytest analytics\tests -q
.\.venv\Scripts\python.exe -m analytics.worker
```

API и .NET Worker запускаются отдельно с `ConnectionStrings__FleetCareDb`, как
описано в остальных шагах проекта. Python читает параметры `PGHOST`, `PGPORT`,
`PGDATABASE`, `PGUSER`, `PGPASSWORD` и `FLEETCARE_KAFKA_BOOTSTRAP` из окружения.
Для локальной разработки их можно записать в корневой `.env`; файл исключён из Git.
На этом компьютере `.env` уже создан и содержит параметры выделенной роли
`fleetcare_analytics_worker`. Роль может выполнять `SELECT` по
`TelemetryReadings`, её транзакции по умолчанию доступны только для чтения.

На другом компьютере создайте отдельную роль PostgreSQL и выдайте ей
`CONNECT` к базе, `USAGE` на схему `public` и `SELECT` на таблицу
`"TelemetryReadings"`. Задайте роль и пароль через переменные окружения или
локальный `.env`; пароль в Git не добавляйте.

## Доставка и повторы

Python подтверждает Kafka offset после анализа и успешной доставки риска.
При сбое он пересоздаёт Consumer и перечитывает неподтверждённое событие.
`riskId` — UUIDv5 от `vehicleId`, типа риска и `sourceEventId`, поэтому
повторная публикация имеет тот же идентификатор. .NET Worker сохраняет
`RiskAlert` и `ProcessedMessage` в одной транзакции, затем подтверждает offset.
Старые тестовые сообщения Kafka без автомобиля или показания в БД помечаются
как обработанные и не блокируют партицию.

## Проверка результата

1. Создайте автомобиль через `POST /vehicles` с большим интервалом ТО.
2. Отправьте через `POST /telemetry` ряд температур из примера выше,
   увеличивая `occurredAt` и пробег для каждого показания.
3. Откройте `http://localhost:5015/dashboard/risks`. Должно появиться одно
   предупреждение с объяснением «Медиана 80 °C; три показания 90/92/94 °C».
4. Нажмите «Проверено» и убедитесь, что статус изменился.
5. Повторно опубликуйте тот же JSON в `risk.detected.v1` с прежними
   `riskId` и Kafka key. Worker должен сообщить `Outcome=Duplicate`,
   количество предупреждений не меняется.
